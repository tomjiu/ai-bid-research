## 1. P1 发现（3 项——全部 Lead 亲读复核实锤）

### AUD2-1 [P1] extract.rs:1117 PDF 主路径 date_cn 参数永不产出【已证实】

`fill_params(&para, &re_model, &re_amount, &re_date, &re_date, &mut params)`——第 5 实参（re_date_cn 槽位）误传 `re_date`，ISO 正则跑两遍。中文大写日期（「二〇二六年十月十五日」——date_cn_regex 注释自称工期/质保主流写法）在 **PDF 主路径永远抽不出 date_cn 参数**。DOCX 侧（1691/1891）与 B1 路径（同为 PDF 块）均正确。跨格式参数面静默分叉，#428 修过的同类病。修复 = 一行 + 仿 veto_cross_format_symmetry.rs 补对称测试。

### AUD2-2 [P1] db.json 跨进程 lost-update 零防护【已证实（代码面）；实际部署形态待验证】

- 原子性达标：store_io.rs:295-325 tmp+write+fsync+rename + #564 瞬态重试——崩溃无撕裂。
- 但全 workspace **无文件锁**（Cargo.toml 无 flock/fs2/fd-lock）；bid-mcp stdio 长进程内存持有全量状态，每次工具调用后 auto_checkpoint **整态覆盖写，不与盘上 content_version 做写前比对**（service.rs:1049-1058）→ 交叉进程后写者静默吞先写者全部变更。
- tmp 名固定 `db.json.tmp`（store_io.rs:298），两个并发写者互踩同一 tmp。
- mang-app/src/bid.rs:23-25 注释明示「bid-mcp-stdio / Agent 改写 db.json 后，下一条命令自动重开」——**双进程共写是设计预期场景**，现防线只有 mang-app 侧指纹重开（防己方读陈旧，防不了 bid-mcp 侧陈旧覆盖）。
- 修法方向：写前 content_version 比对拒绝陈旧覆盖 + tmp 名加 pid/nonce 后缀（fd-lock 级文件锁为重方案，可选）。

### AUD2-3 [P1] songling_baseline 固化门字面量与 manifest 脱钩两个刷新周期【已证实】

songling_baseline.rs:318/322/326 硬编码 `gate_count(..., 11, 11)` / `(..., 0, 13)` / `(..., 9, 8)`；manifest 真源（layer1_pdf_baseline.category_counts）已经 #266/#132/#267/#145 两轮刷新为**技术参数 12 / 商务要求 13 / 评分项 14**。后果：**商务要求从 13 回归到 0 不红灯**（0 ≥ known=0 → FAIL 横幅 + 测试通过）；技术参数 12→11、评分项 14→9 同样不设防。同文件 req_total（:303）与姊妹文件全部走 baseline_u64() 读 manifest——证明此处是遗漏而非口径，且与文件头「manifest 是数据真源」自相矛盾。:320 过期注释（「两路径一致为 0」）同修。
