## 核心发现 1：章节骨架三套完全不同的模板

```
黑龙江组内部 Jaccard：0.95 - 0.96
黑龙江 vs 内蒙古：    0.028   ← 只有 2 个标题重合

HLJ 并集 61 个章节标题
NM  并集 13 个章节标题
交集      2 个（第一章投标邀请 / 第二章投标人须知）
```

| 章 | 黑龙江 | 内蒙古 | 询价 |

| 1 | 投标邀请 | 投标邀请 | `1.适用范围` |

## 核心发现 2：内蒙古文件集带附件格式件

```
黑龙江 5 份：zip 内只有 1 个 PDF
内蒙古 3 份：zip 内 = 主件 PDF + 附件/ 目录（22-27 个格式件）
```

附件内容（节选）：

```
附件/
  中小企业声明函.docx
  主要商务要求承诺书.docx
  技术偏离表.docx
  法定代表人授权委托书.docx
  投标人基本情况表.docx
  项目组成人员一览表.docx
  联合体协议.docx
  残疾人福利性单位声明函.docx
  监狱企业证明文件.docx
  包(1)_开标一览表.pdf
  ... 共 22-27 个
```

**这些是投标人必须填写的官方模板，不是可选材料。** 引擎目前只处理主件。

## 核心发现 3：.doc 格式不被支持

实测（`bid-tools` 直接调两个入口）：

```
==== bid_engine::parse_docx_via_engine(.doc) ====
  ERR: engine rejected: container corrupt: invalid Zip archive: Could not find EOCD

==== bid_parse::parse_file(.doc) ====
  ERR: 不支持的文件类型 .doc（test.doc）
```

**用户实际路径**（`service.rs:374` 的 `_ =>` 兜底）走 `parse_file`，报「不支持的文件类型」——这条是对的。

**但用户把 `.doc` 改名成 `.docx` 自救时**，会报「容器损坏」——错误归因。详见 issue。

## 使用纪律（反过拟合）

### 1. 结论必须标注适用范围

```
当前样本：10 份，3 个平台来源（黑龙江 / 内蒙古 / 未知）
不能说「引擎通用」——只能说「在这 3 个来源上验证过」
```

### 2. 识别规则用形态，不用字面

```
错误：if chapter == "采购需求" -> 技术参数
正确：if 章节含「参数表」或「技术要求」表格 -> 技术参数

错误：if chapter == "评标办法及标准" -> 评分要处理
正确：if 章节含「评审内容 / 分值」表头 -> 评分要处理
```

### 3. 黑龙江组仍是主回归基线

```
batch1（黑龙江 5 份）-> 主回归，GT 红线（L1 >=309/318、否决 >=291/302）
batch2（异源 6 份）  -> 泛化验证，防过拟合
```
